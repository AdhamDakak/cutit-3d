## 1. Product overview

**Cutit** is a mobile booking app for salons and barbershops in Egypt (launching with Cairo). Customers discover venues, pick a stylist + services + date/time, and book. The product vision covers three booking modes:

| Mode | Description | Status in app |
|---|---|---|
| **In-salon** | Book a slot at a venue (barbershop / beauty salon) | UI built end-to-end (mock data) |
| **At-home** | A barber / stylist / coiffeur comes to the customer | UI built end-to-end (mock data) — Cutit Go tab → gender toggle → stylist list → stylist detail → 4-step `go-booking` wizard → confirmation |
| **Events & Bridal** | Makeup artists, bridal packages, event styling | UI built end-to-end (mock data) — same flow as At-Home, plus optional event notes on the address step |

Key product traits:
- **Market**: Egypt. Prices in **EGP**, Cairo districts (New Cairo, Zamalek, Maadi, Heliopolis, Sheikh Zayed), phone-number auth (`+20`), English + Arabic (العربية) language toggle.
- **Personalisation**: the user's profile gender (male/female, asked at sign-up, editable in Profile) decides which salons, stylists and services they see — Home, Explore and Cutit Go. Guests choose with a For Her / For Him toggle on Home (§2.37).
- **Customer-facing only**. There is no venue/partner side (no dashboard for salons to manage bookings, staff, or availability).

### Core user journey
`Onboarding (3 slides)` → `Auth (country code + phone → 6-digit OTP → profile)` or `Continue as Guest` → `Home` → pick a venue or a Cutit Go stylist → services → date/time → `Confirm`. **A guest reaches Confirm with the same rights as a signed-in user** — the account (phone → OTP → name/email/gender) is created in an in-flow sheet at that exact moment, not before; the booking then completes with the same handler. → `Bookings` tab, where the new booking shows under Upcoming with a Pending→Confirmed→Completed status timeline (auto-advances from Pending to Confirmed after a few seconds, mocking the venue/stylist accepting it).

Auxiliary support flow, reachable from the header menu icon, Bookings' "Need Help" link (now booking-aware), or Profile: `Menu` → `Help` (booking summary + Reschedule / Cancel with a confirm dialog / Chat Support) or `Chat Support` directly. Reschedule opens a dedicated `/reschedule` screen reusing the same day-pill/time-slot picker as booking; Cancel and Reschedule are real mutations now, Chat Support is still local-state only, see §5.

    - **Migration.** On load, an old saved user or registry entry with `fullName` is split on the first space (first word → `firstName`, the rest → `lastName`) and 'For Him' / 'For Her' become `'male'` / `'female'`; the migrated value is written straight back.

## 6. State & data model

- **Server state**: fully behind `lib/api/*` + `lib/hooks/*` (see §2.12 and §4). `lib/data.ts` exports the static mock tables and the pure derivation helpers, but a guardrail comment at its top says only `lib/api/*` may import them as values — every screen goes through a hook instead. Concretely:
  - **Pure reads** (`venues`, `stylists`, `services`) are just wrapped in `delay()` + returned — nothing to mutate, so `lib/api/venues.ts`/`stylists.ts` have no store of their own.
  - **Mutable resources** (`bookings`, `addresses`, `favorites`, `reviews`, the current `user`, and since §2.30–§2.34 `cards`/wallet transactions/payment method, support tickets, notifications, chat) each own a private in-memory array/object inside their `lib/api/*` module, seeded once from `lib/data.ts` at import time and never touching the original export again. Each pairs with a `subscribe`/`invalidate` bus (`lib/api/_internal/bus.ts`) so a mutation (`createBooking`, `addAddress`, `toggleFavorite`, `completeProfile`, `createReview`, ...) tells every hook watching that resource to refetch — this is exactly the job a query library's cache invalidation does, and is meant to be deleted wholesale (along with `useAsync`/`useMutation`) the day TanStack Query goes in, without touching any call site. **As of §2.17, `bookings`/`addresses`/`favorites`/`user` also hydrate from and persist to AsyncStorage** (`lib/api/_internal/persist.ts`'s `hydrate`/`persist`, one key per resource under `@cutit/*`) — every exported function `await`s a module-level `ready` promise before touching its store, so a call is never served stale seed data while the persisted value is still loading; since every read already goes through `useAsync`, that brief window shows up as ordinary `isLoading`, not a separate flash. `reviews` joined in §2.27, and every store added since persists from the start — only the go-booking wizard draft is still in-memory.
  - **`lib/api/slots.ts`** is the availability seam: `listSlots(...)` wraps `generateTimeSlots`/`generateStylistTimeSlots`, so a real backend computing this server-side only changes this one function's body.
- **App state** (`lib/app-state.tsx`): session/UI state — `hasOnboarded`, `isSignedIn`, `guestGender` (persisted; content gender while signed out — read it through `useContentGender()`, §2.37), `language` (persisted), `theme` (persisted, §2.17), `remindersEnabled` (persisted, §2.25 — mirrored into `lib/notifications.ts`, since `lib/api/bookings.ts` is a plain module that can't read context), `isHydrated`. **Storage is MMKV since §2.26** (`lib/storage.ts`); wherever this section says AsyncStorage below, read "storage". `isHydrated` gates on every persisted value here — onboarding, session, language, theme, reminders — in one combined startup `useEffect` (still the same `SplashGate` pattern in `app/_layout.tsx`). Since §2.27 `hasOnboarded` and `isSignedIn` persist too (`isSignedIn` is the mock session — a Supabase token in `expo-secure-store` later), and `signOut()` clears only the session. `theme` is owned here but the actual color scheme lives in NativeWind's own imperative `colorScheme` object (from the `nativewind` package, `get()`/`set()`, not its `useColorScheme()` hook) — `toggleTheme()` calls that and mirrors the result to AsyncStorage; `components/app-header.tsx` and `app/(tabs)/profile.tsx` both go through `useAppState()` now rather than reading NativeWind's hook directly, so there's one owner. `bookings`/`addresses`/`favoriteVenueIds` moved to the `lib/api` stores in §2.12 and are now persisted at that layer too (§2.17), not here.
- **Go-booking wizard draft** (`app/go-booking/_layout.tsx`'s `GoBookingDraftContext`): selected service ids, chosen address id, event notes, selected date/time — scoped to the 4-step flow only, deliberately **not** part of shared state since it's meaningless outside an in-progress booking, and **not** part of the §2.17 persistence pass either (still discarded on reload mid-flow, see §9.11). Only the finished `Booking` crosses into the shared `lib/api` store, via `useCreateBooking()`. `eventDate` was removed from this context in §2.18 — it only ever held a freeform text field redundant with the wizard's own date/time step.
- **Venue-detail booking selection** lives in local `useState` inside `venue/[id].tsx` (separate from the go-booking draft above, since salon booking is a single screen, not a wizard) and is discarded once `useCreateBooking()` resolves.
- **Guest checkout draft** (`components/checkout-auth-sheet.tsx`): phone/OTP/name/email/gender fields live in the sheet's own `useState`, reset on close or success — never touches the booking draft it's layered over, and the underlying venue/review screen is never unmounted while it's open (see §2.13).

`lib/data.ts` types (deliberately shaped to match what a real Supabase backend would return — normalized tables keyed by `venueId`/`staffId`/etc., not deeply nested object literals):

```ts
type Venue = {
  id; name; coverImageUrl: string | null; address; area; city; latitude; longitude
  rating; reviewCount; category: 'Barbershop' | 'Beauty Salon'
  gender: 'Men' | 'Women' | 'Unisex'        // the venue's clientele; matched to a person's Gender only via lib/api/venues.ts (§2.37)
  servicesOffered: string[]                  // loose marketing tags (badges/search), separate from the Service catalog below
  description; openingHours: Record<DayOfWeek, { open; close } | null>
}
type Staff = { id; venueId; name; role; photoUrl: string | null; rating? }
type Stylist = {                             // a Cutit Go mobile/event provider — distinct from venue-scoped Staff
  id; name; isFreelancer; venueId: string | null
  serviceTypes: ('at-home' | 'events-bridal')[]
  servesGender: ('male' | 'female')[]        // who this stylist serves, not who they are
  specialties: string[]; rating; reviewCount; bio; photoUrl: string | null; portfolioPhotos: string[]
  priceFrom; yearsExperience?
  availability: OpeningHours                 // same shape as Venue.openingHours, no per-day exceptions yet
}
type Service = { id; venueId: string | null; stylistId?; name; durationMinutes; priceEGP; category }
type TimeSlot = { id; venueId; staffId; serviceId; startTime; endTime; status: 'available' | 'booked' | 'blocked' }
type Address = { id; label; area; details; latitude?; longitude? }
type Booking = {
  id; userId; bookingType: 'salon' | 'at-home' | 'events-bridal'
  venueId: string | null; staffId: string | null
  anyStaff?: boolean                         // true when staffId is null because the customer chose "Any Stylist" — see ANY_STAFF_ID below
  stylistId: string | null; addressId: string | null
  travelFeeEGP?; eventNotes?
  serviceIds: string[]; startTime; endTime; status: 'pending' | 'confirmed' | 'completed' | 'cancelled'; priceEGP; createdAt
}
type Review = { id; bookingId; venueId: string | null; stylistId?; userId; rating; text: string | null; photoUrls: string[]; authorName; createdAt }
type Gender = 'male' | 'female'              // a person's gender (§2.37); "For Her/For Him" are i18n labels only
type User = { id; firstName; lastName; email; phone; avatarUrl: string | null; gender: Gender; addresses: Address[]; walletBalance }
type Favorite = { id; userId; venueId; createdAt }   // a user↔venue join, not an isFavorite field on Venue — matches the Booking/Review pattern
type SavedCard = { id; brand: 'visa' | 'mastercard' | 'meeza'; last4; expMonth; expYear; isDefault }   // never a full number or CVV (§2.30)
type WalletTransaction = { id; type: 'topup' | 'payment' | 'refund'; amountEGP; createdAt; bookingId? }
type PaymentMethodType = 'card' | 'cash' | 'wallet'
type SupportTicket = { id; number /* "CT-1042" */; userId; bookingId: string | null; category; description; photoUrls: string[]; status: 'open'; createdAt }
type AppNotification = { id; type; createdAt; readAt: string | null; bookingId?; ticketId?; params }   // text rendered from i18n at display time (§2.33)
type ChatMessage = { id; from: 'user' | 'support'; text; createdAt; kind?: 'greeting' | 'auto-reply' }   // `kind` messages render from i18n (§2.34)
```

`ANY_STAFF_ID` (`lib/data.ts`, re-exported via `lib/api`) is a **client-side selection sentinel only** — it's what `selectedStaff` holds in `venue/[id].tsx` and what `listSlots(...)`'s `staffId` param recognizes as "no specific staff, check the whole venue's bookings instead." It is *never* what a stored `Booking.staffId` equals: `createBooking` translates it to `{ staffId: null, anyStaff: true }` at write time, so the "any stylist" case is an explicit, typed part of the `Booking` contract rather than a magic string a future backend would have to special-case.

Mock tables: `venues`, `staff`, `stylists`, `services`, `reviews`, `bookings`, `favorites`, `currentUser`, `savedCards`, `walletTransactions`, `defaultPaymentMethod`, `notifications` (one seeded review prompt), (the old fixed `serviceFilters` list was removed in §2.37 — Home's chips come from `listVenueServiceCategories`). `lib/api`'s in-memory stores (see above) seed from these once; `AppStateProvider` no longer touches any of them. Derived-data helpers stand in for what would be backend queries/RPCs — all now called from inside `lib/api/*`, not from screens directly:
- `getVenueStaff/Services(venueId)`, `getStylistServices(stylistId)`, `getStylistsByType(type)` — the joins a real `select('*, staff(*), services(*)')` query would do. (`getVenueReviews`/`getStylistReviews` were removed from here in §2.15 — reviews now have their own mutable store in `lib/api/reviews.ts` rather than a pure derivation over the static table, since `createReview` needs somewhere to write to.)
- `getVenueStartingPrice(venueId)` — cheapest service, not a stored/guessed number; and `isVenueOpenNow(openingHours)` — live-computed "Open"/"Closed" badge. Both are pure/synchronous and re-exported from `lib/api/index.ts` unwrapped (no `delay()`) since they're formatting derivations over data a screen already has in hand, not their own fetch.
- `generateTimeSlots({ venueId, staffId, serviceId, date, durationMinutes? })` — availability from venue hours + existing `bookings` + service duration (a hardcoded lunch-break rule at hour 13 stands in for a real per-staff schedule exceptions table, which doesn't exist yet). Still only checks the **static seed** `bookings`, not the live `lib/api/bookings.ts` store — it has no `bookingsList` override, unlike its stylist counterpart below; a pre-existing simplification carried over as-is during the `lib/api` migration rather than fixed, to keep that migration a pure relocation.
- `generateStylistTimeSlots({ stylistId, durationMinutes, date, bookingsList? })` — same idea for the go-booking wizard and reschedule, reading the stylist's own `availability` instead of a venue's; no lunch-break rule. `lib/api/slots.ts` now always passes the **live** `lib/api/bookings.ts` store as `bookingsList` (optionally minus the booking being rescheduled, via `excludeBookingId`) — this unifies what used to be two different behaviors (the go-booking wizard checked only static seed data, reschedule checked a live list) into one.
- `getBookingDetails(booking, addresses)` — resolves the venue/staff/stylist/address/services for a booking in one call; still synchronous (kept that way to avoid a second round of hook plumbing), re-exported via `lib/api/index.ts` so it's never imported from `lib/data.ts` directly.
- `calculateTravelFee(area)` (`lib/travel-fee.ts`) — flat EGP 50 base fee plus a per-Cairo-area surcharge table (New Cairo 0, Zamalek/Maadi 20, Heliopolis 30, Sheikh Zayed 50, else 40) — a placeholder pricing rule, not distance-based.

The booking lifecycle's mock auto-confirm (`lib/api/bookings.ts`'s `scheduleMockAutoConfirm`, a `setTimeout` that flips a `pending` booking to `confirmed` after 5s) is explicitly commented **MOCK ONLY** — delete the whole function and its two call sites (`createBooking`, `rescheduleBooking`) once a real backend confirms bookings itself.

Screen-local state that isn't in a shared context (each resets on unmount/reload): `menu.tsx`'s row taps, `reschedule.tsx`'s selected date/time, and in-progress form fields on the account/support screens. Chat's messages and draft moved into `lib/api/chat.ts` in §2.34.

## 7. Design system & conventions

- **Palette** (Tailwind defaults): background `#f7f5f1` (light) / `zinc-950` (dark); surfaces `white` / `zinc-900`; text `stone-900` / `white`; muted `stone-500` / `zinc-400`; borders `stone-200` / `zinc-800`; primary actions `stone-900` (light) → `blue-600` (dark, and for CTAs like Confirm/Continue); accents `amber-400` (stars), `emerald` (confirmed/completed status badges), `blue-50/100` (info tints), `red-500` (destructive).
- **No letter-spacing in Arabic** (§2.21): never put a bare `tracking-*` class on text that can be Arabic — wrap it as ``${tracking('tracking-[3px]')}`` from `lib/rtl.ts`. Only the always-Latin `Logo` wordmark is exempt.
- **Start-aligned text under RTL** (§2.22): for a label that should hug the layout's start edge regardless of its own script, use `style={startAlign}` from `lib/rtl.ts`. Don't write a language-keyed `'right'` — RN already flips `textAlign` under RTL.
- **Native-only modules need a web (and Expo Go) story**: `react-native-maps` → a `.web.tsx` platform file with the same props; `expo-calendar`/`expo-notifications` → every call wrapped so it degrades to a message or a no-op instead of throwing; `react-native-mmkv` → lazy `require` in a `try` with an AsyncStorage fallback, because it throws at import time.
- **Typography**: headings use `font-serif` (Fraunces_600SemiBold, via `@expo-google-fonts/fraunces`), body/`font-sans` uses Inter_400Regular — both bundled with `expo-font` so they render identically on iOS and Android, replacing the old Georgia/system-font fallback. Section eyebrows: `text-[11px] uppercase tracking-[3px]`.
- **Shape**: cards `rounded-2xl`, inputs/buttons `rounded-xl`, chips `rounded-full`, consistent `px-5` page gutters.
- **Dark mode**: always pair light + `dark:` classes on `View`/`Text`. For icon colours use `useThemeColors()` (`lib/theme.ts`) because SVG props can't take classNames.
- **Components**: `Pressable` (not `TouchableOpacity`), `expo-image`'s `Image`, `SafeAreaView` with explicit `edges`, `ScrollView` with `contentContainerClassName`. Horizontal lists are `ScrollView horizontal` + `flex-row gap-*`.
- **Files**: kebab-case, one component per file, named exports for components, default exports only for routes.
- **Navigation**: `useRouter().push('/venue/${id}')` for detail; `replace` for auth/onboarding transitions so they're not in the back stack.
- **Card-push screens** use `components/stack-header.tsx` (§2.31) instead of copying the header markup; pass `action` for an end-side button and both side slots widen equally so the title stays centered.
- **Modal screens** (`venue/[id]`, `chat-support`, `help`, `menu`) all share one header shape: a circular bordered back button (`ArrowLeft`, `size-9`, `accessibilityLabel="Close"` or `"Back"`) on the left, a centered `font-serif text-lg font-semibold` title, and either a matching action button or an empty `size-9` spacer on the right to keep the title centered. Reuse this shape for any new modal rather than inventing a new header.
- **Segmented digit input** (`components/otp-step.tsx`): an array of single-char `TextInput`s with a `ref` array, auto-advancing focus forward on entry and back on backspace-into-empty — not a library, hand-rolled since none was installed.
- **Fixed overlay + full-bleed background**: when a screen layers a fixed top/bottom control strip over a full-bleed background (Explore's map, any future full-bleed layout), the fixed strip needs its own opaque page-background color (`bg-[#f7f5f1] dark:bg-zinc-950`) — a transparent strip lets whatever's layered underneath bleed through the gaps between its child elements.
- **Multi-step modal flow** (`app/go-booking/`): when a flow has several internal steps that should all open as *one* modal (not one modal per step), give the group its own `_layout.tsx` with a nested `<Stack>` and register only the group itself as `presentation: 'modal'` in the root `_layout.tsx` — never register the individual step screens. Steps then push as normal card transitions inside the already-open modal. Carry step-to-step selections in a small React Context scoped to that group's `_layout.tsx` (e.g. `GoBookingDraftContext`), not in shared app state — only the final committed result (here, the finished `Booking`) belongs there.
- **In-flow auth over a booking screen** (`components/checkout-auth-sheet.tsx`): when a flow needs to interrupt itself for a short side-task (here: sign-up) without losing the user's place, present it as a `Modal` *over* the current screen rather than navigating to a new route — the screen underneath stays mounted (just visibly dimmed by the modal backdrop), so nothing about its draft state needs saving/restoring. Compose the same step components (`phone-step.tsx`/`otp-step.tsx`/`profile-step.tsx`) the full-screen version uses rather than duplicating the UI; the modal's only job is sequencing them and calling back into the screen's own submit logic on success.
- **Reusable wizard steps as components, not routes**: `PhoneStep`/`OtpStep`/`ProfileStep` accept only data + callbacks (`onSubmit`, `isPending`, optional `title`/`subtitle` overrides) — no navigation, no data fetching of their own — so the exact same UI works both as a full route (`app/auth.tsx`) and inside a modal (`checkout-auth-sheet.tsx`) with different copy and an extra gender toggle in the latter.
- **Falsy-empty-string JSX gotcha**: `{value && <Text>...}` renders a literal (invalid) empty text node when `value` is `''` rather than `undefined`/`false` — bit `components/settings-rows.tsx` once real (possibly-empty-while-loading) data replaced a hardcoded string. Always write conditionals over a possibly-`''` string as `{value ? <X/> : null}`, never `{value && <X/>}`.
- **`expo-image`'s `<Image>` needs `cssInterop` registered before `className` works on native** (§2.15): NativeWind only maps `className` → `style` automatically for React Native's own primitives, not third-party components. `lib/nativewind-interop.ts` registers `cssInterop(Image, { className: 'style' })` once, globally, imported as a side effect from `app/_layout.tsx` — every `<Image>` in the app keeps using `className` as normal and this doesn't need repeating per file. Only reach for an explicit `style={{...}}` prop on an `<Image>` when the values are genuinely dynamic/runtime (e.g. `review-photo-viewer.tsx`'s screen-width/height), not as a workaround for this.
- **Keyboard avoidance over a bottom-sheet-style `Modal` with a `TextInput`**: wrap the `Modal`'s content in `<KeyboardAvoidingView style={{ flex: 1 }} behavior={Platform.OS === 'ios' ? 'padding' : undefined}>` (established in `checkout-auth-sheet.tsx`, reused in `review-modal.tsx`, §2.15; also `go-booking/address.tsx` and `app/auth.tsx`, §2.19) so the keyboard pushes the sheet up instead of covering the input/submit button. Add `keyboardShouldPersistTaps="handled"` to any `ScrollView` inside that content whose children (thumbnails, chips, etc.) should register a tap on the first try while the keyboard is up, rather than the tap first dismissing the keyboard. On a screen with no `ScrollView` at all (`auth.tsx`), the `KeyboardAvoidingView` alone is enough — that prop only applies to a scrollable container.
- **A text input inside an iOS modal sheet (`presentation: 'modal'`)**: don't rely on `KeyboardAvoidingView`. It compares its layout y against the keyboard's *window* y, and a sheet's offset from the window top is applied natively, so RN can't see it (`measureInWindow` doesn't help under the New Architecture). Instead pad the screen's bottom by the keyboard's `endCoordinates.height` on `keyboardWillShow`/`WillHide` (iOS; `DidShow`/`DidHide` on Android), animated with `LayoutAnimation` using the event's duration and curve, and drop the bottom safe-area inset while it's up (`chat-support.tsx`, §2.34). Full-window RN `<Modal>`s (`review-modal`, `checkout-auth-sheet`) and full-screen screens are fine with `KeyboardAvoidingView`.
- **Mirroring an icon for RTL**: put `transform: [{ scaleX: -1 }]` on a wrapping `<View>`, never on the lucide SVG itself, which flips around its top-left corner and slides out of its button (§2.34). Where a mirrored icon exists, swapping it (e.g. `ArrowLeft`/`ArrowRight` by `I18nManager.isRTL`) is simpler still.
- **Stored items render text at display time**: anything saved for later display (inbox items, chat greeting/auto-reply) stores a type/kind + raw params — ISO dates, names, numbers — and builds its text from i18n when shown, so it follows a language switch (§2.33, §2.34).
- **Content gender**: never map a gender to venues/stylists in a screen. Read `useContentGender()` and pass it to `lib/api` (`listVenues({ contentGender })`, `useStylists({ gender })`) or its helpers in `lib/api/venues.ts`. Because the profile arrives a moment after mount, don't copy it into `useState` as a starting value — derive it (`picked ?? contentGender`) or follow it with an effect (Explore), or you'll freeze on the guest default (§2.37).
- **Names**: show `getFullName(user)` only to the user themselves; anything other people can see (review authors, and later anything a venue displays) uses `getDisplayName(user)` — first name + last initial.
- **Card data**: never collect, store or log a full card number or CVV anywhere, not even in mocks or tests; only a payment-partner token + brand/last4/expiry (§2.30).
- **Auto-scrolling a message-style list past a rising keyboard**: `KeyboardAvoidingView` only keeps the composer visible — it does nothing for a list that needs to follow the keyboard up too (`chat-support.tsx`, §2.19). Give the `ScrollView`/`FlatList` a `ref` and scroll to end in two places: whenever the underlying list data changes (new item), and on `Keyboard.addListener('keyboardWillShow'/'keyboardDidShow', ...)` (the keyboard rising can newly cover the tail of an already-static list). A composer becoming visible is not the same as the content above it having followed it.
- **Swipe-to-dismiss on a bottom-sheet-style `Modal`**: use the shared `components/useSheetDismissGesture.ts` hook (§2.18) rather than hand-rolling gesture-handler/reanimated code per sheet — it returns a pan gesture (attach to the sheet's header/handle, never a scrollable body, to avoid fighting a `ScrollView`'s own vertical pan) and an animated style (attach to the whole card). Every sheet built as a plain `<Modal>` + styled `<View>` (i.e. everything except `@gorhom/bottom-sheet`'s own Explore panel) needs its own `<GestureHandlerRootView style={{flex:1}}>` wrapping the `Modal`'s content — gesture-handler doesn't reliably see the app-level one across a `Modal`'s separate native window on iOS. Put the animated `style` on a plain `<Animated.View>` with **no `className`** — it's a third-party-wrapped component like `expo-image`'s `Image` (see the `cssInterop` entry below), so don't assume `className` is styling it; keep all visual styling on a normal `<View>` nested inside it.
- **Single-line `TextInput` vertical centering** (§2.19): `textAlignVertical="center"` alone isn't sufficient on Android — the `text-*` NativeWind classes carry Tailwind's default `lineHeight` (taller than the `fontSize`; check the actual resolved value via `resolveConfig()` against `tailwind.config.js`, don't assume), and centering that taller line-box still lets an empty field and a typed character render a hair differently. Pair `textAlignVertical: 'center'` with an explicit, tighter `lineHeight` close to the `fontSize` in the same `style` object (e.g. `text-sm`'s 14px font → `{ fontSize: 14, lineHeight: 18 }}`, not the default 20). Multiline fields are the opposite case — use `textAlignVertical="top"` (centering a growing block makes it visibly jump as it wraps) and leave their `lineHeight` alone, *unless* the field is short enough to behave like a single line at rest (`chat-support.tsx`'s `min-h-11` compose box uses `"center"` for exactly this reason).
- **Persisting a `lib/api/*` store** (§2.17; MMKV under the hood since §2.26 — never call MMKV or AsyncStorage directly, go through `persist.ts` or `lib/storage.ts`): use the shared `lib/api/_internal/persist.ts` pair — `hydrate(key, seed)` once at module load (assign its resolved value into the module-level store variable) and `persist(key, value)` inside a `setStore()` wrapper that every mutation calls instead of assigning the store directly. Every exported function must `await` the module-level `ready` promise from `hydrate()` before reading or writing the store, including any internal helper another module calls directly (e.g. `bookings.ts`'s `getBookingsSnapshot()`, used by `slots.ts` — it had to become `async` for exactly this reason). Because every read already goes through a `lib/hooks/*` `useAsync` hook, this needs no separate loading UI of its own — `isLoading` already covers the brief hydration window, the same way `app-state.tsx`'s `isHydrated` flag covers `language`/`theme` for state that isn't behind a hook.

## 8. Known limitations & gotchas

- ~~State and theme reset on reload.~~ Resolved (§2.17, §2.26, §2.27, §2.34): everything persists on MMKV now except the go-booking wizard draft.
- ~~Map, location, calls, directions, notifications are all placeholders~~ Map, location, calendar, and local reminders are real now (§2.23–§2.25); calls and directions are still placeholders, and the map is a placeholder on web only.
- **Native features run only in the dev client.** Expo Go has no MMKV (falls back to AsyncStorage), no `expo-calendar` new API (Add to Calendar shows the failure line), and local notifications behave differently there; web has none of maps/calendar/notifications. Test these on the EAS dev build.
- ~~Opening the app from a reminder still goes through onboarding first.~~ Resolved in §2.27: onboarding persists and `index.tsx` routes a cold-start reminder tap straight to Bookings.
- **Right after launch, a signed-in user's content briefly follows `guestGender`** until their profile loads (`useContentGender` falls back to it), so Home can flash the other gender's venues for a moment (§2.37).
- **Signing up inherits the demo user's data.** `completeProfile` overwrites the one seeded mock user in place (keeping its id), so a new account gets that user's sample bookings, addresses, wallet and cards. Now that guests can't see that data (§2.32) it's more noticeable right after sign-up.
- **The Menu still shows Sign Out to guests**, unlike Profile (§2.32).
- **Review and report photos are stored as the picker's local file paths**, and iOS can purge the picker's cache, so a persisted photo may later fail to load. Text and ratings are safe. Copy them into the app's documents folder, or wait for real uploads.
- **The go-booking flow is an iOS sheet with a KeyboardAvoidingView** on its address step, so its event-notes field probably sits too low under the keyboard — the same problem Chat Support had (§2.34). Not fixed yet.
- **Chat Support's keyboard padding on Android** may double up if Android also shrinks the window for the keyboard; if so, apply the padding on iOS only (§2.34).
- **Reminder text is fixed when the reminder is scheduled**, in the language active at that moment; switching language later doesn't rewrite already-scheduled reminders.
- App icon/splash/adaptive-icon are real Cutit branding now, but it's a quick mark derived from the wordmark's scissors motif, not final polished brand design — worth a real design pass later. `Logo` itself is still the text placeholder on purpose (the real wordmark SVG caused a native crash — "Element type is invalid" — most likely because the dev client needed a restart to pick up the new `metro.config.js` transformer; re-wire it via `assets/images/cutit-logo.svg` once that's confirmed fixed on-device).
- Images are hot-linked from Unsplash / pravatar — fine for demos, not for production.
- No ESLint/Prettier config (`expo lint` will prompt to create one), no tests, no CI — the `lib/api` guardrail (§2.12, §4) is therefore a comment + a manual grep, not an enforced lint rule; see §9.4 to add one.
- `expo-env.d.ts` is generated and gitignored; TypeScript needs it for `*.css` imports — it's created on first `expo start`.
- The Explore/Home duplication from v0 was intentionally split: Home = discovery + list, Explore = map/list. ~~Explore lacks the service filter chips.~~ Resolved in §2.14 — Explore now has its own full filter sheet (categories, gender, price, rating, distance, open-now) plus real search.
- **Testing dark mode**: ~~NativeWind's color scheme on web is in-memory only, so a full page reload doesn't toggle it~~ — since §2.17, `theme` is persisted (`@cutit/theme`) and re-applied on hydration, so a real `page.reload()` now correctly restores it too (confirmed live: toggled to dark, reloaded, still dark). A browser context's *emulated* `prefers-color-scheme` still won't touch it either way, since the app only follows the system scheme at first launch (`colorScheme.get()`'s initial value), not reactively afterward.
- **Testing the Explore bottom sheet**: synthetic mouse-drag gestures (e.g. Playwright) can land on an underlying list item instead of the sheet's drag handle and trigger a tap/navigation instead of a drag. Start the drag precisely on the handle, not generic mid-screen coordinates. The same caution applies to the swipe-to-dismiss gesture added in §2.18 on every other bottom sheet — a synthetic drag is unreliable evidence either way; verifying the *tap*-to-close X button still works is the more trustworthy web check, and was what was actually used to verify §2.18's sheets.
- **Testing with Playwright, post-persistence**: `page.goto(...)`/`page.reload()` is a full reload, but as of §2.17 it **no longer wipes** `bookings`/`addresses`/`favorites`/`user` — those now round-trip through AsyncStorage (`localStorage` on web) and rehydrate correctly (confirmed live: favorited a venue, reloaded, still favorited). Since §2.27 it no longer wipes `hasOnboarded`/`isSignedIn`/reviews either — seed `cutit\@cutit/onboarded` / `cutit\@cutit/signed-in` in `localStorage` (MMKV's web keys are prefixed `cutit\`; write the backslash as `'\\'` in a JS string) to start a test signed in. To verify a mutation to a *still-unpersisted* resource actually happened within a session, keep navigating client-side rather than reloading. Also, ambiguous text like `getByText('Explore')` can match "Explore both" on Home before it ever reaches the Explore tab label — prefer `{ exact: true }` for short nav labels.
- **`react-native-web`'s `Alert.alert()` doesn't support multiple custom-labeled buttons** — only a plain native OK/Cancel confirm renders there (if anything at all), losing custom labels and per-button `onPress` handlers. This affects every multi-button `Alert.alert` call in the app: the Cancel-booking confirm dialog in `help.tsx` (2 buttons), the photo-source picker in `usePhotoPicker.ts` (3 buttons, used by reviews and reports), and the delete-address and remove-card confirms (§2.29, §2.30) — so those flows are untested until the device pass. **Confirmed as intentional, not a gap to fix**: since web is layout-preview-only here and the real target is Expo Go/dev-client, these are verified on-device/simulator only and deliberately have no web-specific fallback branch.
- **A third-party component's `className` isn't automatically styled by NativeWind on native** unless that component registers `cssInterop` (§2.15/§7) — `expo-image`'s `<Image>` needed this (fixed globally in `lib/nativewind-interop.ts`), and any *other* new non-RN-primitive component styled with `className` (a future icon library's custom wrapper, a third-party card component, etc.) needs the same check before assuming `className` "just works" there, since it can look fine on web and be silently unstyled on-device. `react-native-reanimated`'s `Animated.View` (§2.18) was treated with the same caution — never given a `className` at all, only a plain `style`, rather than assuming it inherited `View`'s NativeWind support.
- **`react-native-web`'s `<TextInput>` renders as a real HTML `<input>`/`<textarea>`, so it can't reproduce Android-specific native `TextInput` rendering quirks** — the line-height-vs-`textAlignVertical` text-drift bug fixed in §2.19 is exactly this: real on Android, invisible on web regardless of what the code does. Web testing for this class of bug can only confirm "no crash, text isn't accidentally shrunk" — never that the actual native behavior is fixed. That check needs a real device or simulator.
